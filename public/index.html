Why Starboard

Stop letting one platform's code be the spec.

A product starts from one design, then each release lets the platforms drift. Soon the answer to "what should this screen contain?" is whatever shipped first, and every other platform copies its accidents. Starboard keeps the answer in the repository instead.

A shared reference

A screen registry with stable IDs, named layout regions and the source files that build each screen on each platform. Flows are Markdown: a Mermaid diagram and steps that name screens by ID.

Consistent across platforms

Every platform adapts the same reference, not each other. Starboard draws grey-box wireframes for each form factor, an app map and a screen catalog, so a review shows what changed.

Catch drift in CI

A formatter and a linter with stable rule IDs and JSON output. One command fails the build on a broken reference, an unformatted file or a stale generated page.

Drift caught in CI

The GitHub Action downloads the release you pin, checks its SHA-256 against the release's checksums and runs starboard lint. Every rule has a page, like file-missing or generated-stale.

Leading and following

One platform can lead. Every platform follows the reference.

A change starts as proposed in the reference and is reviewed like code. Whichever platform builds it first marks it shipped there; the others follow the same text, and status is kept per platform until they catch up.

  1. 1

    Define

    Record screens, regions and flows as text in screens.yaml and flows/.

  3. 2

    Adapt

    Build the reference on each platform, and link each screen to the source files that implement it.

  5. 3

    Verify

    Lint in CI, and review the generated catalog, wireframes and app map in the pull request.

Platforms

One product. Multiple platforms.

These are the platforms your product targets, each with the form factors its wireframes are drawn at. You name them in starboard.yaml.

  • iOS

    Usually phone; add tablet in starboard.yaml.

  • Android

    Usually phone; add tablet in starboard.yaml.

  • Web

    Drawn at web-narrow and web-wide, each with its own layout.

  • Desktop

    macOS, Windows or Linux apps, drawn at desktop, with windows.

The starboard command itself runs on macOS, Linux and Windows, on amd64 and arm64.

Developer experience

Built for your repository.

Starboard is one binary and a few plain files beside your code. There is no server and no account; reviews happen in pull requests.

Built for agents

  • Skills for Claude Code, Cursor, Copilot, Codex, Gemini and Aider, installed with starboard skills install.
  • starboard lint --json: findings with stable rule IDs an agent can act on.
  • Hooks: a Claude Code hook and a pre-commit hook that run starboard fmt and starboard lint; other agents get the same steps as instructions.
