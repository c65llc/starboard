Your first project

This page starts a Starboard project from nothing: a trip-planning app with two screens on iOS and the web, and one flow that goes between them. Every command and file on this page is run by Starboard’s own tests, in this order, so what you see is what you get.

Run the commands at the root of your app’s repository. Starboard keeps everything in plain files there: starboard.yaml and a docs/flows/ directory.

Create the project

Section titled “Create the project”

init lists every file it writes:

  • starboard.yaml is the project’s configuration. Its directory is the project root: every command finds the project by looking for it, from the working directory upward.
  • docs/flows/screens.yaml is the registry: one entry per screen. init writes one example screen, home.main.
  • docs/flows/flows/example.md is an example flow.
  • docs/flows/generated/ is written by starboard generate. Never edit it by hand.
  • docs/flows/README.md tells people who find the directory what it is.
  • .gitattributes gets three lines that keep these files’ line endings the same on every operating system. Keep them.

Register your screens

Section titled “Register your screens”

Add a trip area for the second screen. Edit starboard.yaml:

Then replace the example screen in docs/flows/screens.yaml with two of your own: the list of trips, and one trip’s timeline.

Each screen has a stable dotted ID (home.trips), a title, an area, a purpose and a presentation: how a person gets there (root, push, tab, sheet, dialog, window or route). Its layout is a tree of named regions, each of a fixed kind such as list or primary-action. A to: is a link to another screen. See Screens and regions.

The example flow still refers to home.main, which is gone, so delete docs/flows/flows/example.md.

Now format the files, regenerate generated/ and check the project:

  • fmt rewrites files that are not in canonical form and lists them. These files already were, so it printed nothing.
  • generate wrote the app map, the screen catalog and one wireframe per screen per form factor, and removed the example screen’s wireframes.
  • lint found no errors, and two warnings: no flow mentions either screen. Warnings do not fail lint unless you pass --strict. Each finding names its rule; orphan-screen explains this one.

Commit it

Section titled “Commit it”

Commit starboard.yaml, .gitattributes and docs/flows/, generated pages included: they are what people read on GitHub, and lint checks they match the sources. Then check the reference in CI, so it cannot fall out of date.

If you work with a coding agent, install Starboard’s skills next, so the agent edits the reference the same way: see Working with coding agents.
