JSON output and rules

starboard lint --json and starboard rules --json print one JSON document each, for CI annotations, editors and coding agents. Both carry "version": 1; a change that breaks a reader will bump it. Rule IDs are stable strings, so act on the rule, not on the wording of the message.

lint --json

Section titled “lint --json”

A project with a problem in each of three rules, and its generated pages up to date:

The text report, one finding per line and then the count:

The same findings as JSON:

errors and warnings are always arrays, empty when there is nothing to report, and sorted by file, then line. Each finding has:

Field Value
rule The rule’s ID.
severity error or warn.
file The file, relative to the project root, with /.
path Where in the file: a dotted path into the YAML, such as screens.trip.timeline.layout[0], or "" for the whole file.
line The 1-based line, when there is one; left out otherwise.
message What is wrong, in a sentence.
fix When Starboard can fix it: {"description": …}, saying how. starboard lint --fix applies the fixes for formatting and generated pages.
docs The rule’s page: https://starboard.c65llc.com/rules/<rule>/.

The exit status is the same as without --json: 1 when there is an error, or a warning under --strict. With --fix, the list of files it wrote goes to stderr, so stdout stays one JSON document.

rules --json

Section titled “rules --json”

Each rule has its id; its kind, correctness or quality; its default severity; a one-sentence summary; and its docs page. Rules are sorted by ID.

Rules

Section titled “Rules”

Correctness rules are always errors. Quality rules default to warn (and pass lint unless you use --strict); lint.rules in starboard.yaml can make one an error or turn it off. Each rule’s page says what it catches, why it matters and how to fix it.
