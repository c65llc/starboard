CLI

starboard works on the project that holds the working directory: it looks for starboard.yaml there, then in each parent directory. Every example on this page runs, as written, in Starboard’s tests: the commands that need a project against a copy of examples/travel-app, and init in an empty directory.

Usage

Section titled “Usage”

starboard <command> --help prints one command’s usage and flags. Flags may come before or after a command’s arguments.

Global flags

Section titled “Global flags”
Flag Meaning
--dir D Work in directory D instead of the working directory. It comes before the command.

--dir changes where the project is looked for, not how paths you type are read: render -o is still relative to the working directory.

Exit status

Section titled “Exit status”
Status Meaning
0 The command succeeded, with nothing to report.
1 Findings: lint found errors (or warnings, with --strict); fmt --check or generate --check would change files; fmt or generate found errors in the project; or fmt could not format a file.
2 A usage error, no starboard.yaml in the directory or any parent, or a command that could not run.

starboard init

Section titled “starboard init”

Writes a new project in the directory: starboard.yaml, docs/flows/README.md, docs/flows/screens.yaml with one example screen, docs/flows/flows/example.md, the generated pages, and lines in .gitattributes that keep the files’ line endings the same on every operating system. It lists every file it writes. It refuses, changing nothing, if any of the files it would write already exists.

Flag Meaning
--platform P Add platform P; ios, android and web get suggested settings. Repeat it for each platform.

A platform other than ios, android and web starts with no settings; add its formFactors, roots and screenFiles yourself. See Your first project.

starboard fmt

Section titled “starboard fmt”

Rewrites starboard.yaml, screens.yaml and every flow file in canonical form, and lists each file it changed. Canonical form fixes key order, indentation and the order of screens; it keeps comments. Formatting a formatted file changes nothing, and a file whose only difference is CRLF line endings counts as formatted.

Errors in the project are printed to stderr and make fmt exit 1, but every file that can be formatted still is. A file fmt cannot format safely is reported as cannot format <path>: <reason>.

Flag Meaning
--check List the files fmt would change, change nothing, and exit 1 if any.

starboard lint

Section titled “starboard lint”

Checks the project and prints each finding, then a count. Correctness findings are always errors; quality findings are warnings unless starboard.yaml sets their severity. lint exits 1 when there is an error. It includes the checks fmt --check and generate --check make, as the rules not-formatted and generated-stale.

Flag Meaning
--json Print the findings as a versioned JSON report. See JSON output.
--fix First format the sources and regenerate <content>/generated, listing each file, then lint. A project with errors that stop it loading is not fixed. With --json, the list goes to stderr.
--strict Exit 1 on warnings as well as errors.

A finding reads <file>:<line>: <severity> <rule>: <message>, with the line left out when there is none. Each rule has a page at https://starboard.c65llc.com/rules/<rule>/; JSON output lists them all.

starboard rules

Section titled “starboard rules”

Lists every lint rule: its ID, whether it is a correctness or a quality rule, its default severity and a one-sentence summary. It needs no project.

Flag Meaning
--json Print the rules as a versioned JSON report, each with its documentation page.

starboard generate

Section titled “starboard generate”

Writes <content>/generated/: app-map.md, screens.md and one wireframe per screen per form factor under wireframes/. It writes only files whose content changes, prints wrote <path> for each, and removes, printing removed <path>, a wireframe it no longer generates, such as a deleted screen’s. It never touches other files under generated/. A project with errors that stop it loading is refused, with exit status 1.

Flag Meaning
--check List what generate would write or remove, change nothing, and exit 1 if anything.

--check prints would write <path> and would remove <path>.

starboard render

Section titled “starboard render”

Prints one screen’s wireframe as SVG, the same bytes generate writes for it. It is for trying out a layout without regenerating everything.

Flag Meaning
--form-factor F Draw form factor F (default: the screen’s first). Any configured form factor works, not only the screen’s own.
-o FILE Write the SVG to FILE, an .svg path relative to the working directory or absolute, instead of stdout.

-o must end in .svg, so it can never overwrite a source file, and it writes the file whole or not at all. An unknown screen or form factor is a usage error, exit 2.

starboard schema

Section titled “starboard schema”

Prints the JSON Schema for starboard.yaml (config) or screens.yaml (screens). It needs no project. See JSON Schemas.

starboard mcp

Section titled “starboard mcp”

Serves the project to a coding agent over the Model Context Protocol: JSON-RPC messages, one per line, on stdin and stdout. The agent’s MCP client starts it; you do not run it by hand. Its tools query screens and flows, follow references, lint, render wireframes and make formatted edits; the MCP server reference lists them. It exits 0 when stdin closes.

Flag Meaning
--read-only Leave out the tools that write files: starboard_screen_set, starboard_flow_set and starboard_generate.

Stdout carries only the protocol. Stderr gets one line naming the project, then one line per tool call, with its outcome.

starboard skills install

Section titled “starboard skills install”

Installs Starboard’s agent skills for each coding agent the project already uses, or for each --agent. Without --agent, it detects the agents from files at the project root, such as .claude/ or AGENTS.md, and stops if it finds none. Files you have edited since Starboard installed them are kept, and the new version is staged under .starboard/pending/. Working with coding agents covers the details.

Flag Meaning
--agent A Install for agent A: claude-code, cursor, copilot, codex, gemini or aider. Repeat it for each agent.
--dry-run List what install would write or stage, and change nothing.

starboard skills list

Section titled “starboard skills list”

Lists the skills this release carries, with what each is for.

starboard skills hooks

Section titled “starboard skills hooks”

Prints configuration that runs starboard fmt and starboard lint after edits, and edits no file: a Claude Code hook for claude-code, a git hook script for pre-commit, and for cursor, copilot, codex, gemini and aider, which have no edit hook, a paragraph for the agent’s instructions file. A note on where to put it goes to stderr.

starboard skills mcp

Section titled “starboard skills mcp”

Prints the MCP client configuration that makes the agent start starboard mcp, and edits no file: JSON for claude-code (.mcp.json), cursor (.cursor/mcp.json), copilot (VS Code’s .vscode/mcp.json) and gemini (.gemini/settings.json), and TOML for codex (~/.codex/config.toml). Aider has no MCP client, so aider is a usage error. A note on where to put it goes to stderr. It needs no project.

Flag Meaning
--read-only Configure the server with --read-only.

starboard version

Section titled “starboard version”

Prints starboard and the version: the release’s for a release binary, the module’s for go install, and dev for a build from a source checkout.

Internal commands

Section titled “Internal commands”

starboard hook claude-code is not in the usage: it is the command the Claude Code hook that starboard skills hooks claude-code prints runs after each edit. It reads the hook’s input on stdin, and exits 2 with the findings when the edited file breaks the reference, which Claude Code hands back to the agent. See Working with coding agents.
